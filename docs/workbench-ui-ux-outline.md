# Kunora Workbench UI/UX 文字大纲

## 1. 设计目标

工作台围绕一个主流程设计：**关联 Git 仓库分支 → 完成任务基础信息与任务方案 → 通过启动门禁 → 交给 dsh 执行 → 持续查看、控制和交互**。[BIZ-02][BIZ-03]

本阶段只定义信息架构、页面职责、状态和关键交互。视觉风格、组件规格、响应式规则、静态稿和交互稿在本大纲确认后继续设计；任务分支内的目录结构与结构化文件格式另行定义。[BIZ-02]

## 2. 核心对象

| 对象 | UI 中的含义 |
| --- | --- |
| 任务 | 一个 Git 代码仓库中的一个分支，是工作台管理和执行的基本对象。 |
| 任务基础信息 | 独立于六要素的任务描述，至少包括任务名称和任务介绍。 |
| 任务定义 | 任务基础信息、任务级六要素、总体方案和路线图的集合。 |
| 六要素 | 最终目标、整体工作方法、边界、约束、交付物、验收；验收下分验收标准和验收方法。 |
| 路线图 | 由有顺序的里程碑组成，用于表达任务的推进路径。 |
| 里程碑 | 路线图中的阶段对象，最终需要自己的六要素、总体方案和详细计划。 |
| 执行 | 任务通过中央服务分配给后端节点，并由 `dshd + dsh` 实际完成的过程。 |

## 3. 启动门禁

“启动任务”是工作台最重要的状态转换，必须由界面明确解释，而不是只显示一个不可点击按钮。

| 检查项 | 首次启动是否必须 | UI 表现 |
| --- | --- | --- |
| 已关联有效的仓库与分支 | 是 | 显示仓库、分支及关联状态。 |
| 任务名称和任务介绍完整 | 是 | 分别显示完成或缺失状态，并可直接进入基础信息编辑。 |
| 任务级六要素完整 | 是 | 按要素逐项显示完成或缺失状态。 |
| 任务级总体方案完整 | 是 | 显示完成状态，并可直接进入编辑。 |
| 路线图已明确 | 是 | 至少能识别里程碑及其顺序；具体完整性规则在路线图数据定义时冻结。 |
| 每个里程碑的六要素 | 否 | 显示里程碑完善进度，不阻止任务首次启动。 |
| 每个里程碑的总体方案和详细计划 | 否 | 显示里程碑完善进度，不阻止任务首次启动。 |

门禁未通过时，主操作显示“还差 N 项”，同时列出缺失项并允许一键定位。门禁通过后，主操作变为“启动任务”。

## 4. 信息架构

MVP 工作台只保留两个一级空间：

1. **任务列表**：关联任务，浏览所有任务及其定义和执行状态。
2. **任务工作区**：围绕单个任务完成定义、路线图维护、启动、执行交互和结果查看。

任务工作区内部按任务当前阶段呈现三个连续区域：

- **定义**：任务基础信息、六要素、总体方案、路线图和启动门禁。
- **里程碑**：查看里程碑顺序及完善各里程碑的定义和计划。
- **执行**：启动后查看进展、实时输出，并与 dsh 交互或发起控制操作。

## 5. 页面大纲

### 5.1 任务列表

- 页面主操作是“关联任务”。
- 每个任务以一行显示：任务名称、任务介绍摘要、仓库、分支、定义状态、执行状态、当前进展和最近更新时间。[BIZ-03]
- 基础信息尚未填写完整时，不自动编造任务名称或介绍；列表以仓库和分支保持任务可识别，并明确标记缺失内容。[BIZ-02][BIZ-03]
- 定义未完成的任务突出“待完善”，主操作是“继续定义”。
- 已通过门禁但未启动的任务突出“可启动”，主操作是“查看并启动”。
- 已启动任务显示执行状态和进展，主操作是“进入工作台”。
- 空状态只解释如何关联第一个仓库分支，不展示无关指标。

### 5.2 关联任务

- 采用聚焦的对话框或独立步骤页。
- 建立关联的必要输入仅包括代码仓库和分支；任务名称和任务介绍可在关联后进入任务定义页补充，但在补充完成前不能启动任务。[BIZ-02][BIZ-03]
- 提交前验证仓库、分支是否可识别，并明确显示即将关联的唯一对象。
- 关联成功后立即进入任务工作区，同时该任务已经出现在任务列表中。
- 关联成功不等于可以启动；首次进入时应直接展示启动门禁和缺失项。

### 5.3 任务定义页

- 顶部固定展示任务名称、仓库/分支、定义状态和“启动任务”主操作。
- 主内容依次展示基础信息、六要素、总体方案和路线图；基础信息至少提供任务名称与任务介绍的查看和编辑。[BIZ-03]
- 六要素使用同一编辑结构；验收部分明确分为验收标准与验收方法。
- 路线图以有序里程碑列表呈现，支持查看顺序和进入里程碑详情。
- 侧栏或固定摘要区展示启动检查清单；点击缺失项定位到对应编辑区。
- 保存后立即重新计算门禁状态，避免用户手动刷新或重新检查。

### 5.4 里程碑详情页

- 顶部显示里程碑名称、顺序及完善进度。
- 内容由里程碑六要素、总体方案和详细计划组成。
- 未完善内容明确标记，但不与整个任务的首次启动门禁混淆。
- 返回路线图时保留编辑位置和任务上下文。

### 5.5 启动确认

- 只在启动门禁通过后可进入。
- 确认信息包括任务、仓库、分支和任务定义摘要。
- 明确告知启动后将由中央服务选择后端节点，并交给 `dshd + dsh` 执行。
- 用户确认后进入“启动中”反馈状态；禁止重复提交。
- 调度或启动失败时保留任务定义，展示可理解的失败原因和重试入口。

### 5.6 执行工作区

- 主区域用于与 dsh 收发消息、查看实时输出和处理任务执行中的交互。
- 持续展示任务执行状态、总体进展和当前里程碑。
- 提供任务控制入口；具体控制动作以 Harness 已有能力和后续产品定义为准。
- 可随时返回查看任务定义、路线图和里程碑详情，不丢失当前执行上下文。
- 结果和成果以关联 Git 分支为主，工作台呈现执行状态与结果入口。

## 6. 核心交互流程

### 6.1 关联并定义任务

1. 用户在任务列表选择“关联任务”。
2. 用户指定 Git 仓库和分支。
3. 工作台建立关联，任务立即进入列表，状态为“待完善”。
4. 用户进入任务定义页，依次完善任务名称与介绍、六要素、总体方案和路线图。
5. 工作台实时检查缺失项；未通过时阻止启动并解释原因。
6. 全部必需信息明确后，任务状态变为“可启动”。

### 6.2 启动并执行任务

1. 用户选择“启动任务”并核对任务摘要。
2. 工作台向中央服务提交启动请求。
3. 中央服务分配后端节点，并把任务路由给对应 `dshd + dsh`。
4. 工作台进入执行工作区，持续接收状态、进展和实时信息。
5. 用户在同一工作区继续交互、查看结果或发起受支持的控制操作。

### 6.3 完善里程碑

1. 用户从路线图进入一个里程碑。
2. 用户补充该里程碑的六要素、总体方案和详细计划。
3. 工作台更新里程碑完善进度，但不反向改变已经满足的任务首次启动资格。

## 7. 状态表达

任务列表和任务工作区使用两组状态，避免把“定义是否完整”和“是否正在执行”混成一个状态：

- **定义状态**：待完善、可启动。
- **执行状态**：未启动、启动中、执行中，以及后续由执行生命周期定义的终态或异常状态。

里程碑单独显示完善进度，不使用任务执行状态。状态以文字为主，颜色只用于辅助识别。

## 8. 静态稿范围

本大纲确认后，静态稿优先覆盖以下五个关键画面：

1. 已有关联任务但定义未完成的任务列表。
2. 基础信息或任务方案部分完成、启动门禁未通过的任务定义页。
3. 门禁全部通过、可以启动的任务定义页。
4. 内容尚未完善的里程碑详情页。
5. 任务启动后的执行工作区。

静态稿首先确定桌面 Web 工作台的信息层级、布局和状态表达，再决定是否需要移动端适配。

## 9. 交互稿范围

交互稿应串联一条完整主路径：**关联分支 → 任务进入列表 → 补齐基础信息与任务方案 → 门禁解锁 → 确认启动 → 进入执行工作区**，并至少覆盖以下反馈：

- 关联失败或分支不可识别。
- 必需信息缺失及一键定位。
- 保存后门禁状态更新。
- 启动请求处理中防重复提交。
- 调度或后端启动失败后的保留与重试。

## 10. 后续单独定义

以下事项不在本轮文字大纲中提前决定：

- Git 分支内的任务目录结构与结构化文件格式。
- 仓库接入、凭据、权限和分支冲突规则。
- 六要素、总体方案、路线图和详细计划的字段级数据格式。
- 任务启动后的具体控制动作和执行终态。
- 多人协作、版本历史、审核和发布规则。
